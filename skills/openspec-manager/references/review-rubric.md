# OpenSpec 评审维度矩阵 (Review Rubric)

作为评审者，你必须针对每个 Capability 和 Scenario 提出以下三个维度的问题。

## 1. 业务闭环 (Business Loop)

**核心目标：确保流程逻辑自洽，没有“断头路”。**

- **逆向流程**：如果用户中途取消、退款或操作失败，系统是否有对应的反向处理逻辑？
- **状态机完备性**：实体（如订单、账户）的所有可能状态是否都在 Spec
  中定义？是否存在无法跳出的死循环状态？
- **外部依赖补偿**：如果第三方系统（如支付网关）超时，我们的业务流程是挂起、重试还是回滚？
- **财务/审计合规**：该操作是否产生了不可追溯的资金或权限变动？是否有日志留痕？

## 2. 技术可行性 (Technical Feasibility)

**核心目标：确保方案在当前工程环境下可落地、高性能。**

- **数据一致性**：在并发场景下，是否会出现“超卖”或数据覆盖？是否需要引入分布式锁或事务？
- **性能边界**：当数据量达到百万级时，Scenario
  中的查询逻辑是否依然有效？是否存在 O(n) 的循环调用？
- **幂等性**：如果同一个请求被重复发送（如用户连点、网络重试），系统是否能保证只处理一次且结果一致？
- **扩展性**：当前的 Schema 设计是否为未来可能的变动预留了字段？

## 3. 安全性 (Security)

**核心目标：秉持“零信任”原则，防止恶意利用。**

- **权限控制 (IDOR)**：用户 A 是否可以通过修改 ID 来操作用户 B 的数据？每个
  Scenario 是否都校验了操作者权限？
- **输入合法性**：是否对所有外部输入进行了格式、长度和类型校验？是否防御了 SQL
  注入或 XSS？
- **限流与防刷**：该功能是否会被机器人利用（如：暴力破解、恶意刷票）？是否有频率限制？
- **敏感数据处理**：日志或数据库中是否明文存储了密码、秘钥或个人隐私数据？
